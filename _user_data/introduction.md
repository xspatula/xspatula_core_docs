User data — records you want to store in the database — must be in JSON format. But instead of writing JSON files, you can also add data from Excel or CSV spreadsheets. The framework converts them to JSON formatted process files and then inserts the records into the appropriate database table.

There are two ways to do this:

1. **Two-step route** — run `translate_tabular_data` to convert a spreadsheet to a JSON process file, then run that generated file with a second, separate step to insert the records. Handled by `./project_example/import_data/load_utility_data.ipynb`. Use this when you need to update existing records, start from a JSON source with no spreadsheet, or want to inspect or hand-edit the generated JSON before it's applied.
2. **Single-step route** — run `insert_tabular_data` to translate and insert in one step, with no manual hand-off. Handled by `./project_example/import_data/insert_utility_data.ipynb`. Use this when you just want a spreadsheet's rows in the database and don't need to inspect the generated JSON or ever update existing rows through this route — see [Single-step insert][single_step_insert] for the full walkthrough.

The rest of this section documents the two-step route, since it's the more general of the two; the single-step route is a faster alternative for the common case.

## Prerequisites

Before loading user data, both of the following must be complete:

- [Setup DB][setup_db] — the database must exist with the target schema and table
- [Setup processes][setup_processes] — the `translate_tabular_data` and `manage_territory` processes must be registered in the database (the single-step route additionally requires `insert_tabular_data` to be registered)

## The project_example

The repository includes a worked example in `project_example/` that imports national territory data into the `utility.territory` table. The source data is a spreadsheet of ~200 countries with their ISO 3166-1 alpha-2 codes. This example is used throughout this section to illustrate each step.

## Project file structure

```
project_example/
├── scheme_xspatula.json            # scheme file — project path + user credentials
└── import_data/
    └── utility/
        ├── excel/
        │   └── territory.xlsx      # source spreadsheet
        ├── process/
        │   └── territory.json      # process definition for translate step
        └── manage_process/
            └── manage_territory.json   # generated by translate step, used by insert step
```

The single-step route adds a parallel `insert_process/` structure alongside this one — see [Single-step insert][single_step_insert] for details.

## Scheme file

The scheme file for the example project points to the `project_example` directory and uses an `ini_cat_5_user` login:

```json
{
  "project_path": "../project_example",
  "user_project": {
    "user_name": "ini_cat_5_user",
    "password": "armchair-scouting-windowframe-bicycling"
  },
  "process": [
    {
      "execute": true,
      "verbose": 0,
      "overwrite": false,
      "delete": false
    }
  ]
}
```

Replace `user_name` and `password` with your own credentials. You can also use `user_netrc_id` to read credentials from a [.netrc file][netrc].
